# Plan 05-02 — Post-Rollback Recovery Verification Loop

**Phase**: 05 — Rollback Execution & Recovery Verification
**Plan**: 05-02
**Wave**: 2
**Depends on**: 05-01
**Objective**: Implement the post-rollback recovery verification loop in Deploy Monitor Agent with stabilization cooldown, multi-iteration telemetry polling, strict multi-metric evaluation, and state persistence.

## Proposed Changes

### Deploy Monitor Agent & Verification Loop

#### [MODIFY] [deploy_monitor.py](file:///home/zeph/Code/deployguard/src/deployguard/agents/deploy_monitor.py)
- Extend `DeployMonitorAgent` to support recovery verification mode (`verify_recovery` method / pipeline branching):
  1. Stabilization cooldown: Wait for a configurable delay (default 2s in test/demo mode, D-03) to let services stabilize after rollback.
  2. Multi-iteration sampling: Poll telemetry from `MetricsSource` over 3–5 iterations at 1s intervals across all 7 metric dimensions (error rate, latency, crash rate, CPU, memory, restart count, request rate).
  3. Strict recovery evaluation (D-04):
     - Compare sampled metrics against `state.baseline_metrics`.
     - `recovered`: All 7 metric ratios drop below anomaly threshold (<= 1.15x baseline, 0 crashes/restarts across iterations).
     - `degraded`: One or more metrics remain anomalous above threshold.
     - `inconclusive`: Metrics query throws an error, returns empty telemetry, or times out.
  4. Update workflow state:
     - `state.recovery_verdict = verdict`
     - `state.recovery_checked_at = datetime.now(UTC)`
     - `state.pipeline_status = "complete"` (if recovered) or `"failed"` (if degraded/inconclusive).
  5. Yield `Event` describing verification verdict and evidence summary.
